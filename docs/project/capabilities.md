# Project Capabilities

## Purpose

This document provides a stable capability-level view of what the project currently provides. It is especially useful for long-lived products and multi-module systems where milestones alone do not answer what the system can do today.

Adopting projects should replace the template capabilities below with product or system capabilities that matter to maintainers and stakeholders.

## Template Capabilities

| Capability | State | Notes |
| --- | --- | --- |
| Documentation-first project knowledge | Available | Durable project knowledge has focused authoritative locations. |
| Multi-assistant AI collaboration | Available | Codex, Claude Code, and Cursor share one repository contract. |
| Structural code intelligence | Available by policy | Graphify is the required adopting-project baseline. |
| Optional broader code search | Optional | Sourcegraph may be adopted when justified. |
| Progressive context routing | Available | Agents load only task-relevant context. |
| Long-term delivery-state recovery | Available | Roadmap, status, and capabilities expose current state. |
| Focused debug/refactor context | Available | Module context, Graphify, source, tests, and decisions form a bounded path. |
| Developer documentation | Available | Dedicated developer-guide area exists. |
| User documentation | Available | Dedicated audience-facing user-guide area exists. |

## Maintenance Rules

- Track externally meaningful or architecturally meaningful capabilities, not individual classes or tickets.
- Keep state current when a capability becomes usable, limited, deprecated, or removed.
- Keep implementation detail in source, architecture, module documentation, or issues rather than expanding this table indefinitely.
