# AI Collaboration Contract

## Purpose

This document keeps work recoverable when a project moves between Codex, Claude Code, Cursor, and human developers. The repository, not an assistant session, is the durable collaboration surface.

## Canonical Context

- `AGENTS.md` is the shared discovery pointer for repository-aware assistants.
- `CLAUDE.md` is a thin Claude Code adapter back to the shared contract.
- `docs/ai/bootstrap.md` is the authoritative project-wide AI workflow and context-routing contract.
- Tool-specific or generated rules may describe tool mechanics, but they must not duplicate or contradict project-wide guidance.

## Durable Knowledge Ownership

Store durable information according to what it represents:

| Information | Durable location |
| --- | --- |
| Project purpose and constraints | `docs/project/vision.md` |
| Delivery order | `docs/project/roadmap.md` |
| Current delivery state | `docs/project/status.md` |
| Current system capabilities | `docs/project/capabilities.md` |
| Architecture and boundaries | `docs/architecture/` |
| Accepted durable decisions | `docs/decisions/adr/` |
| Proposals needing discussion | `docs/decisions/rfc/` |
| Complex subsystem context | `docs/modules/` |
| Developer procedures | `docs/guides/developer/` |
| User procedures | `docs/guides/user/` |
| Fine-grained execution work | Issue/project tracker |
| Implemented behavior | Source and configuration |
| Expected/verified behavior | Tests |
| Structural map | Graphify-derived project artifacts |
| Historical implementation change | Git commits and pull requests |

Do not use assistant chat history, hidden memory, or a local uncommitted note as the only record of information another contributor will need.

## Handoff Between Assistants

Before switching tools after material work:

1. Leave the working tree in a deliberate state: committed/pushed when the task is complete, or clearly marked when work is intentionally incomplete.
2. Update durable documentation, project status, capability state, ADR/RFC, or issues when the work changed them.
3. Ensure relevant tests or validation results are reproducible from the repository when practical.
4. Refresh Graphify after material source changes according to the project's integration workflow.
5. Record unresolved blockers or follow-up work in the project tracker or the appropriate durable document, not only in the departing assistant's conversation.

The receiving assistant should start from repository state and the bootstrap, not attempt to reconstruct the previous assistant's private reasoning.

## Tool Adapters

Keep assistant-specific entry files small. A tool adapter may:

- point to the canonical bootstrap;
- load tool-specific project integration generated by the tool;
- specify mechanics that exist only in that tool.

A tool adapter must not redefine architecture, coding standards, project status, or cross-agent workflow.

## Conflict Resolution

When tool output, generated code intelligence, documentation, and source disagree:

1. Verify exact current source and configuration.
2. Check relevant tests and current contracts.
3. Correct stale derived data or documentation.
4. Record a decision if resolving the conflict establishes a new durable architectural rule.

Do not silently preserve contradictory sources of truth.
